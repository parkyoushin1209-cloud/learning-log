- UVM의 기본 concept
1. SV_OOP
2. 재컴파일 없이 테스트, 테스트벤치 구조를 명시하게 해주는 동작으로 생성된 객체
3. 에이전트, 드라이버, bus functional model등을 포함하는 계층적 TB 조직
4. 객체 사이 트랜잭션 수준 소통
5. 테스트벤치 구조로부터 분리된 테스트벤치 스티뮬러스(UVM 시퀀스)

각각 다른 기능을 하는 구성요소의 경우 하나의 파일에 두면 
=>재사용 어려움, 디버그 어려움, 유지 보수 어려움
=> 분리시켜 테스트벤치의 다른 부분을 다른 테스트벤치에서 재사용 가능하고 스티뮬러스같은 테스트벤치의 일부를 쉽게 수정 가능하도록

-현대 테스트 벤치의 모든 요소
1. functional coverage goals - 테스트벤치는 테스트의 리스트에 의존하지 않고 테스트한 것들을 측정함
2. self-checking - 파형, 출력 텍스트를 일일이 확인할 필요 없음 -> 원하는만큼 테스트 실행해도 문제 없음
3. constrained random stimulus - 모든 연산을 위한 테스트를 일일이 작성할 필요 없이, 간단히 커버리지 요구사항을 이행하는 CRS 생성

-Bus Functional Goals
인터페이스를 통해 테스트벤치 내 모든 신호 캡슐화, 여러 태스크 제공
=> 테스트벤치의 나머지 부분이 신호 레벨 자극을 무시할 수 있도록 신호 레벨 자극 문제를 다룸

-캡슐화의 장점 
1. 프로토콜 수준 동작을 코드 여기 저기에 넣어둘 필요 없음(신호들을 처리하는 코드보다 태스크를 호출하는게 더 쉬움)
2. 하나의 장소에서 모든 프로토콜 동작을 수정 가능함(또한 여기에서의 수정 사항은 코드 전체로 전달 가능)

-OOP의 장점
재사용성 측면: 객체는 데이터, 태스크, 함수등을 포함함 한 번 정의시 내부에 대해 걱정 필요 없음
재사용은 테스트벤치가 추가되는 모든 함수와 함께 더 강력해짐을 의미
(새 기능을 정확히 프로그래밍 했다면 이 기능을 통해 다른 기능도 추가 가능)

유지보수성 측면: 
하나의 테스트벤치에서 다른 테스트벤치로 코드를 복사했을 경우 잘못된 점을  발견하면 찾아다니면서 고쳐야 함
다른 사람의 코드를 가져와 사용하는 경우 그 사람이 문제를 발견하고 고쳤다면 동기성도 벗어남

메모리 관리
객체 생성, 테스트벤치에서의 전달은 메모리를 할당하고 프로그램 내 스레드 사이의 공유를 의미
C와 같은 전통적 언어에서 이 것은 고통스럽고 버그 많으나 순수 OOP에서는 쉬움

-OOP는 코드 재사용성을 위해 분류를 이용함 
구조체의 경우 
우리는 두 구조체 사이의 관계를 알아도 프로그램은 모름 => 상속, 다형성 이용
시뮬레이터는 변수를 선언하자마자 메모리를 할당했음 => 핸들만 선언한 경우 핸들에 대해 충분한 메모리를 할당하고 객체의 경우는 new를 통해 할당 가능
사용자가 수식을 모른다면 면적을 계산하는 등의 행위 불가 => 메서드로 정의해둘 경우 몰라도 문제 없음
