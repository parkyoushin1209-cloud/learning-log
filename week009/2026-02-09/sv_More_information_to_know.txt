물리적 인터페이스를 top에만 두는 이유
1 top만이 “실체”를 알아야 함
interface 실체(physical)는: 실제 시뮬레이션 신호, DUT에 직접 연결됨
=> 탑 책임임

2 test / env는 "연결 대상"만 알면 됨
test, environment, driver, monitor는:
이게 진짜 interface인지 어디에 붙어 있는지 알 필요 없음
그냥: virtual alu_if vif; 만 있으면 충분함

3 재사용성과 구조 분리
이 구조를 쓰면:
interface 교체 가능
DUT 바뀌어도 test 재사용 가능
여러 DUT 인스턴스에도 대응 쉬움
=> UVM이 이 구조를 강제하는 이유

가상 인터페이스를 받는 부분
시간 흐름에 따라 DUT 신호를 직접 만지는 컴포넌트만 가짐
"핀을 만지거나 샘플링하면 vif 필요, 데이터만 만지면 필요 없음"
가짐: drv, mon, env, test  안 가짐:gen, scb cov, callback_obj
DUT는 실제 하드웨어 블록이라서 직접 물리적 interface를 가지고 있고, 시그널에 직접 접근하는 주체가 아니거든

  top에서만 물리적 ifc / dut, test는 따로 
  top에서는 종합으로 넘겨줘도(Utopia) test에서 (Utopia.Rx)가 인자로 있으면 Rx모드포트로 접근함
  top에서는 필요한 개수만큼 Utopia 객체를 만들어 넘겨주기(rx, tx가 필요하면 두 개 넘겨주기, 배열 형태로 말고 독립되게)
========================================
  
드라이버 DUT 모니터 트랜잭션 주고 받는 법
열거형/클래스 핸들 등을 ifc의 input, output으로 둬서 전달은 불가능하나 그 클래스가 packed 구조체의 bit/logic으로만 돼있으면 전달 가능
=> pack, unpack이 필요한 이유

top에서 생성하는 클럭의 경우 
시스템 기준 클럭, DUT 내부 FSM,파이프라인,스케줄링용임 dut에만 들어감(DUT의 내부 동작 기준 클럭)

interface 내 clk_in/out은
프로토콜 신호, ATM/Utopia 링크 타이밍용 => 링크클럭은 DUT가 만듦
송신기면 clk_out 생성 수신기면 clk_in기준으로 샘플링
데이터가 언제 유효한가를 나타내는 인터페이스 레벨 클럭

TB는 클럭을 모른다, 관찰만 함, 만들지 않고 dut가 만든 거 따라감(clk_out)
네트워크/링크 관점에서 클럭도 데이터의 일부임

두 클럭이 완전히 무관하지는 않으며 dut에서 비율만 맞춤
