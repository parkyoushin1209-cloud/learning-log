커버리지 데이터 수집
각 시뮬레이션은 기능적 커버리지 정보의 데이터 베이스 생성 
-> 기능적 검증을 통한 전체 진척도 측정을 위해 정보를 병합
-> 
커버리지 진척도가 꾸준히 상승 중 =>  여러 랜덤 시드를 이용해 반복적으로 테스트 수행
느려짐 => 제약 추가 가능
정체기 => 더 많은 테스트 생성 필요

->100% 근접시 버그가 여전히 발생하면 몇몇 부분에 대해 정확한 측정이 안된 것일 수도 있음

각 시뮬레이션 벤더는 커버리지 저장을 위한 포멧, 분석 툴을 가짐
분석툴을 이용해 아래 과정을 실행함
-여러 시드로 테스트 실행
unix system clock을 시드로 사용가능하나 여러 일을 동시에 수행하므로 중복된 결과를 가져올 수도 있음
이 일은 여러 서버를 사용하거나 여러 프로세서가 있는 단일 서버에서 실행 가능
적절히 조정해서 고유시드 생성, 시드,시뮬레이션, 커버리지 결과를 함께 저장해 regression testing에 이용할 수 있게하기

-pass/fail 체크
실패한 시뮬레이션에서 나온 결과는 의미가 없다
또한 디자인 명세에 맞지 않는 경우도 마찬가지다

-여러 실행을 통한 커버리지 분석
각 제약집합이 얼마나 성공적인지 측정할 필요가 있다.
제약으로 타겟팅한 영역에서 100%도달은 아니나 꾸준히 증가중 => 더 많은 시드로 반복
커버리지 수준이 정적임 => 제약 수정
마지막 하나의 특정 섹션의 코너 케이스 도달에 너무 오래 걸릴듯하면 directed test 작성도 고려, 다른 섹션에서는 random stimulus 계속 생성(background noise가 버그를 찾을 수도 있음)

coverage type

code coverage
RTL 코드를 얼마나 잘 테스트 했는지
디자인에서 하나의 코드 블록을 잊었더라도 캐치 못하고 100% 실행됐다고 보고할 수 있음
line coverage: 코드의 마지막 줄까지 실행됐는지
path coverage: 코드, 표현식을 통과하는 어떤 경로가 사용됐는지(if, case 문, 논리식, 조건식 등)
toggle coverage: 변수가 0 또는 1 값을 가진 적이 있었는지
FSM coverage: 상태, 상태전이 전적을 나타냄


--------------------------

functional coverage
검증목표는 설계가 실제 환경에 정확히 동작하는지 확인하는 것임
디자인에서 하나의 코드 블록을 잊어버리면 그 기능 없다고 보고할 수 있음
------------------------------------------
Bug rate
프로젝트 시작 시 테스트 벤치를 생성하면서 여러 버그를 찾을 수 있음(명세서와 일치하지 않는 내용을 찾는 등)
테스트 벤치가 가동되면 시스템의 각 모듈에서 많은 양의 버그를 찾을 수도 있음
tape-out에 가까워질수록 버그 비율이 0에 가깝게 떨어짐
비율이 떨어질 때마다 코너 케이스를 생성할 다른 방법 찾기
버그 비율은 프로젝트 동안 여러 요소에 근거해 변할 수 있음(프로젝트 단계, 최근 디자인 수정, 블록 통합 등)
-------------------------------------------------------------------
assertion coverage
assertion은 절차적으로도 사용될 수 있으며 주로 복잡한 프로토콜 등에서 사용
system verilog assertion을 사용해서 간단한 조건 체크도 가능, 사용하기 더 쉬움
assertion coverage를 통해 어써션이 얼마나 자주 실행됐었는지 확인 


----------------------------
functional coverage strategies
데이터가 아닌 정보를 모아라
중요한 검증 대상은 일반적으로 모든 데이터들이 아님
모든 비트가 1이었다가 0으로 넘어가는 경우, 또는 값의 범위 내에서의 최대, 최소 부분등을 검증하는게 좋고
그 사이의 모든 값에 대해서는 전부 검증할 필요는 없음 데이터에 근거하지 않고 정보에 근거해 데이터 수집

정말로 사용할 거만 측정해라
기능적 커버리지 데이터 수집에는 비용이 든다. 따라서 분석, 테스트 상향을 위해 사용할 것만 측정
시뮬레이션은 시뮬레이터가 기능적 커버리지를 위한 신호를 모니터링하기에 느려질 수 있지만 파형 추적, 코드 커버리지보다 적은 오버헤드를 가진다

측정 완성도
(low code/functional coverage)버그 비율은 프로젝트 시작 지점에서 높게 나타남
테스트벤치를 작성하고 테스트를 실행하면서 각 모듈에서 많은 에러를 발견할 수도 있음

(low code coverage/high functional coverage)
코드의 마지막까지 도달하지 못하는 경우 검증 계획에 문제가 있는 것일 수 있음
처음으로 돌아가 하드웨어 명세를 재확인하고 검증 계획 수정하기

(high code coverage/low functional coverage)
높은 코드 커버리지를 가짐에도 functional coverage가 낮게 나온다면
디자인이 필요한 명세를 모두 구현했는지 확인
모두 구현했는데도 기능적 커버리지가 낮게 나온다면 formal tool 사용하기

(high code coverage/high functional coverage)
커버리지가 높게 나온다고 해서 끝났다고 가정하기는 이름
만약 버그 비율이 적다면 그 검증 방법의 효율성이 떨어진 것일 수 있음
-> 제약을 추가하는 등 검증 방법을 수정하자
