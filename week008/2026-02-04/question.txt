1. generate는 언제 사용하는가?
파라미터 값에 따라 회로 구조 자체가 달라질 때 사용

언제 쓰는가?(대표적인 경우)
1. 반복적인 하드웨어 인스턴스 생성(같은 모듈이나 로직을 여러 개 만들어야 할 때, 비트 수/채널 수/ 레인 수 같은 게 파라미터로 정해짐)
2. 파라미터에 따른 조건부 하드웨어(기능 ON/OFF, 구조 선택-> 합성 시 둘 중 하나만 실제 회로로 생성)
3. 파라미터화된 설계 (Scalable Design) (ex. 파라미터 설정 값에 따라 합성되는 포트 수가 달라지는 등 확장 가능한 RTL에 사용)
4. 구조적으로 계층 이름이 필요할 때 -> 디버깅, 제약(SDC), 커버리지에서 유용

언제 안 쓰는가?
1. 런타임 조건 (always / if) ->동작 제어이며 generate가 아님->generate는 컴파일/엘라보레이션 시점
2. 단순 for-loop로 충분할 때

generate vs always for 차이
| 구분          | generate             | always + for        |
| -------       | -----------          | ------------        |
| 시점          | 엘라보레이션(컴파일) | 시뮬레이션(런타임)   |
| 목적          | 구조 생성            | 동작 반복           |
| 파라미터 영향 | 구조 자체 변경       | 구조 동일            |
| 인스턴스 수   | 변함                 | 고정                |
**파라미터 값에 따라 회로의 모양이 달라지면 generat/ 신호 값에 따라 동작이 달라지면 always*

2. 인터페이스에 모드 포트가 있을 때 스코어보드, 모니터, 드라이버 등의 레이어드 테스트벤치의 구성요소들에는 모드포트를 사용하지 않아도 되는가?
그렇다, 보통은 모드포트를 지정하지 않은 virtual interface를 클래스 인자로 받음, 실제 제약은 interface 쪽 modport로 검.
클래스에서 modport를 잘 안 쓰는 이유
1. 유연성(재사용성)
클래스(driver, monitor, scoreboard)는 여러 역할에 재사용되며 설정에 따라 행동이 달라질 수 있음
클래스 인자에 modport를 사용할 경우:
virtual bus_if.drv_mp vif;  -> 이 클래스는 drv_mp 전용이 되어버림
같은 클래스를 monitor 용도로 재사용하기 어려움
-> virtual bus_if vif; 사용 

3. 그렇다면 modport는 왜 사용하는가?
1. interface 내부에서 역할 분리를 위해
각 구성요소가 뭘 구동할 수 있는지를 구조적으로 제한
(입출력 + 신호명 조합으로 모드포트 기준 뭐가 입력이고 뭐가 출력인지 확인 가능)
컴파일러가 modport를 강제하진 않지만, 설계 규칙상 "이 클래스는 드라이버다"

-> 
인터페이스에는 modport를 둔다 (역할 정의), 
클래스는 보통 modport 없는 virtual interface를 받는다 (유연성), 
전용 드라이버 클래스라면 modport 써도 괞찮다
