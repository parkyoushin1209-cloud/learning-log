B. 커버리지 데이터 분석
일반적으로 더 많은 랜덤 시드와 더 적은 제약이 필요하다고 가정하기, 새 제약 생성보다 더 많은 랜덤 시드로 테스트하는 게 더 쉬움 + 
제약을 주의해서 생성하지 않으면 검색 범위를 제한해버릴 수 있음
커버포인트가 0 또는 1번만 샘플된 경우 이 제약이 다른 영역을 타겟팅하고 있다고 판단(solver를 새 지역으로 옮기기 위한 제약 필요함)

class Packet;
rand bit[2:0] hdr_len;
rand bit[3:0] payload_len;
rand bit[4:0] len;
constraint length{
    len == hdr_len + payload_len; // 이 거만 쓰면 고르게 안나오고 최소, 최대 근처 값이 적게 나옴
    solve len before hdr_len, payload_len; //solve .. before의 대안으로 dist도 가능 => 랜덤화 실패할 수도 있음
}
endclass

C. 시뮬레이션 도중 커버리지 측정하기
시스템 태스크 $get_coverage => 전역공간에 둬서 전체 커버그룹의 커버리지를 계산해 총 커버리지 반환
더 낮은 지역에서 get_coverage() : 인스턴스, 커버그룹 타입의 커버리지 반환 가능 get_inst_coverage() : 인스턴스 레벨 반환
오랜 시간에 걸쳐 테스트할 때 커버리지 확인에 유용(커버리지 진척이 없으면 시드 바꾸거나 테스트 변경)

기능적 커버리지 결과에 근거해 액션을 바꾸는 테스트는 매유 좋으나 이런 종류의 테스트 작성은 매우 어렵다.
테스트가 100% 커버리지에 도달하지 못한다면 랜덤 시드를 바꾸기(시뮬레이션 당 한 번씩만 여러 개 바꾸면 재현하기 어려워짐)

원하면 기능적 커버리지 통계를 조회해 자체 커버리지 데이터베이스를 생성 가능함

D. 결론
directed test -> constrained random test는 자신의 통제권을 잃어버리는 것 처럼 보일 수 있으나
커버리지 결과를 확인하고 어떤 기능이 테스트 돼지 않았는지 확인하며 통제권을 다시 얻게됨

기능적 커버리지 이용은 상세한 검증 계획 설정, 커버그룹 생성, 결과 분석, 적절한 자극을 생성하도록 테스트를 수행하는 데 많은 시간을 요구함
(이는 할 일이 많아 보일 수 있으나 directed test를 직접 전부 작성하는 것보다 훨씬 효율이 좋음)
커버리지 수집에 사용하는 시간을 디자인 검증의 진척도 측정에 도움을 줌
