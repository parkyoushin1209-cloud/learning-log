인터페이스, 매크로, 콜백, 블루프린트 등등은 필요에 따라 추가
인터페이스의 경우 => 
각 구성요소의 클래스 정의에 가상 인터페이스(top에 실제) 주로 dut의 좌(driver) 우(monitor)에만 인터페이스를 만들어주며 CPU/HOST 모델을 위한 인터페이스나 AXI같은 양방향 프로토콜을 위한 인터페이스 등을 만들 수 있음
+인터페이스는 드라이버 / 모니터용 클로킹블록(모드포트)를 분리하여 레이스 컨디션을 방지하고 방향성을 명확히 함
+TB/DUT=> TB 인터페이스는 DUT 포트를 감싸는 추상화 계층이며 DUT는 기능 신호만, TB는 검증을 위한 부가 구조를 포함

설정 클래스의 경우 => 제약, 에러/ 경고 수를 나타내는 integer 값을 가짐/ +런타임 동작 제어용 knob (enable/disable, mode 선택)

드라이버 - 제너레이터 동기화 구현하기(이벤트나 메일박스 2개 사용하는 방식, +peek/get 분리를 통해 pre_tx 콜백에서 트랜잭션 drop/modify 가능)

콜백의 경우 =>
드라이버는 pre,post 커버리지는 pre,post 모니터는 post를 주로 가짐
base 콜백 클래스의 pre, post는 확장된 모든 클래스들을 위한 인자리스트를 가져 다형성을 사용 가능하도록 또한 pre, post에 pure을 쓰지 말고 함수의 몸체는 비우기
+콜백은 순서 의존성이 있으므로 큐 삽입 순서가 의미를 가짐 (앞 콜백의 수정 결과가 뒤 콜백에 전달됨) -> typedef 적극 사용하기

트랜잭션 => 베이스 트랜잭션에서 확장을 해주며 만듦
+트랜잭션은 driver–monitor–scoreboard 간 공통 언어이며 pack/unpack 또는 compare 메서드를 포함할 수 있음


<테스트 벤치 기본 구조>
top 모듈(인터페이스 배열, clk.rst 설정, dut,test 인스턴스화, 파라미터 설정

testbench(환경 객체 생성 및 각 단계 진행 필요시 hook 이용(build-run 사이에서 콜백, 블루프린트 조절 가능) cfg를 조절하고 싶다면 클래스 정의 후 gen_cgf 이전에 객체 지정하게)
(필요시)cgf 클래스 확장 및 핸들로 가리키게
new => mailbox, cfg 객체 생성, 모든 virtual interface 할당
gen_cgf => cgf 랜덤화
build => 각 구성 요소 생성(드라이버, 모니터, 스코어보드 등등)
(필요시) blueprint, callback 생성 후 큐에 삽입
run => 각 구성 요소 실행 및 콜백 -> 드라이버/모니터, 커버리지콜백 -> 모니터
*run 단계는 non-blocking으로 각 컴포넌트를 병렬 실행하며 종료 조건은 test 또는 scoreboard에서 관리

wrap_up => 각 구성요소 wrap_up()

DUT 논리적으로 TB와 같은 종류, 개수의 인터페이스를 가져야 하나 TB보다 적다면 문제 없음(많으면 검증 구멍 생김)

++++TB 구조는 DUT 변경에 강하고, 시나리오/커버리지 확장에 유연하도록 설계됨
