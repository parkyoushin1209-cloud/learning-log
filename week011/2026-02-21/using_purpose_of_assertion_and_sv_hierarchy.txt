어써션
요구 사항 명백히하고 디자인 에러 감지하는데 도움됨
기능적 커버리지 보조에도 사용 가능(특정 프로퍼티나 이벤트의 시퀀스등이 발생했는지 결정해서 테스트 케이스의 효율설 측정하게 해줌)

sv와 문법적으로 통합된 어써션은 디자인 유닛, RTL코드, 다른 검증 코드에 내장된 어써션으로 정의 가능
=> 툴로 하여금 주의 코드 문맥으로부터 대량의 정보 추론할 수 있게 함
(ex. 어써션/형식 검증으로 사용된  제약으로 명시된 예상 동작과 실제 RTL 동작을 비교해 불일치 감지 가능)

테스트벤치와의 상호작용(커버리지, 일시적 조건 집합에 따르는 이벤트, 시퀀스의 종료시점, 에러 등을 전달해서)

어썬션 기반 검증은 예상된 연산, 디자인 의도를 형식적으로 특성화함을 도와줌
검증 주제를 안내하고, 검증속도 가속화(화이트 박스 수준으로 피드백 제공 + 검증자 작업을 어써션에 맡김으로써 TB 설계도 쉬워짐)

SVA는 검증환경 재활성도 허용(어써션 결과에 따라 다른 동작 수행 가능)
하드웨어 가속기에도 사용 가능(RTL 디자인 파트로 합성되거나 하드웨어 에뮬레이션으로 파티션화 됨으로써)
에뮬레이션동안 디자인 로직이 버그를 가지면 합성된 어써션은 에뮬레이션 정지를 위해 정지/추적 레지스터를 트리거하고 실패의 원인을 알려줌

실리콘에도 합성될 수 있으며, 검증 중 버그를 기록하고 플래그를 지정할 수 있음(JTAG 바운더리 스캔을 통해 가능)
SVA를 사용한 형식 검증은 시뮬레이션 없는 다른 검증 레벨을 추가


설계/검증 고려 사항
1. 디자인 타입: 제어 중심적 또는 처리 중심적
FSM을 사용하는 제어 중심적 디자인은 SV, VHDL이 적합함
필터링 유형 설계나 이미지 프로세서같은 처리 집약적 설계는 c/c++ 기반 플로우가 더 효율적일 수 있음
c/c++ 플로우는 verilog/sv를 대체하지는 않을 것임(RTL과 가장 잘 맞는 IP 연결이 여전히 있으므로)
하지만 몇몇 벤더의 IP는 c++으로부터 생성되어 고수준합성을 이용해 verilog, VHDL , systemC 모델로 전환됨
c/c++ 를 이용한 시뮬레이션은 SV 대비 1400배 빠르며 개발 시간도 단축 시킴

2. 엔지니어 지식 및 관리 유연성
설계팀이 VHDL에만 익숙하면 SV with UVM을 전화하는 것에 많은 비용이 들어감(교육비, 도구 구매비, 학습 곡선 등)
팀의 기술력, 일정에 따라 언어 선택 필요

3. 검증 방법론
검증 방식이 언어를 결정함
UVM처럼 제약 조선이 있는 랜덤 테스트, 트랜잭션 기반 접근 방식, 커버리지 분석에는 SV가 적합
어써션 기반 검증, 형식 검증은 SVA, PSL 같은 언어 사용 가능

 SVA의 간결함은 어써션 리뷰, 작성을 빠르게 해주므로 설계 요구사항, 구현을 검증하고 분명히하는데 좋음
SVA는 4개 계층으로 정의됨

1.Boolean 
특정 시간에 참인지 거짓인지 판별하는 논리식
ex. req, req ==1'b1, data =8'hFF

2. sequence
여러 클럭 주기에 걸쳐 발생하는 불리언 식을의 선언적 나열
복잡한 시퀀스는 병렬 분기를 가질 수 있으며 동시에 시작되고 각 사이클 순서대로 지정
기본적으로 시퀀스는 여러 시간 동안 불리언 표현식과 정규 표현식을 매치하려고 함
ex. @(posedge clk) req ##1 ack ##1 write 

3. property
시퀀스, 불리언, 다른 프로퍼티 등 부차적인 것들 사이의 논리적/시간적 관계, 특정 연산자를 모은 집합
실제 환경에 대한 가정이나 커버리지 타겟을 묘사하거나, 특정 시나리오 집합의 분석을 일시적으로 제한하는데 쓰일 수 있음
프로퍼티 선언에서 선언될 수 있으므로 프로퍼티의 재사용 및 인스턴스화를 허용함
툴이 선언된 어써션에 반하는 DUT 검증등의 행동을 하게 하는 어써션 문 내에서도 사용 가능
ex. $rose(req) |=> ack ##1 wr // req 상승시 다음 사이클에 ack가 오고 그 다음 wr이 와야 함

4. directive
프로퍼티 인스턴시에이션을 생성하고 프로퍼티가 성공/실패 했을 때 취해져야 하는 행동을 정의함
프로퍼티 자체는 툴이 수행해야할 검증이나 커버리지 요구 사항은 제공하지 않음
설계 동작, 기능적 커버리지, 그것의 프로퍼티, 그것의 수행에 대한 가정의 옳음을 체크하기 위해 sv는 다음의 어써션 문(directive라고도 불림)을 제공함
assert, assert property, cover, cover property, cover sequence, assume, assume property

Assertion or assert // 상황에 따른 정의, 라벨, 프로퍼티, 동시/즉각적 어써션
어써션 정의는 그것의 문맥에 의존함 일반적인 대화나 개괄적인 설명에서 SVA 언어를 구성하는 assert, assume, cover 지시어들의 전체 부류로 자주 불려짐(상세 문서에서는 특정 assert directive로)
assert는 특정 프로퍼티가 시도될 때마다 반드시 유지돼야하는 문장이며 검증 툴이 프로퍼티 값을 확인하게 하는 문장일 수 있음
프로퍼티는 프로퍼티 선언을 사용해 명명될 수 있으며 어써션은 명명된 프로퍼티로부터 만들어질 수 있음
어써션은 툴에 의해 추적될 수 있도록 라벨을 가질 수 있다
즉각적 어써션은 클럭에 동기화되지 않으며 assert directive를 가진다
동시 어써션은 클럭킹 이벤트에 의존하며 assert property문을 가진다
ap_req_ack_wr : assert property(@(posedge clk) $rose(req) |=> ack ##1 wr)
// 매 상승에지에서 req가 상승하면 다음 사이클에 ack==1 다음 사이클에 wr==1

Assumption or assume //
고려해야할 동작의 범위를 제한하는 제약이며 주로 입력 신호에 적용됨
보통 형식검증에서 주로 사용되나 제약 조건 위반이 플래그로 표시되는 시뮬레이션, 문서화에도 유용함
제약은 리셋을 위한 클럭 사이클 수, 입력에서 합법적인 값처럼 실제 요구사항을 나타낼 수도 있음
형식 검증 툴은 검색 공간 제한을 위해 제약을 사용하기도 한다
랜덤 스티뮬러스 생성기는 또한 유용한 랜덤 벡터 생성을 위해 제약을 사용하기도 함
Assumption은 assume ,assume property문을 사용함
m pRequestReady : assume property(@(posedge clk) not (request && !ready)); //ready 가 false 면 request 금지

Restriction
restirct는 형식 검증에서 분석이 수렴되도록 시나리오를 제한하는데 사용됨(반면 assume은 합법적 입력 상태를 정의함)
분석 성능을 향상시키며, 계산 완료를 위해 사용됨

Functional coveage or cover
기능적 커버리지는 시퀀스나 프로퍼티가 최소 한 번은 발생하도록 보장하는 기술임
=> 발생 여부, 요구 사항을 확인함
cover, cover sequence, cover property문을 사용하며 assert, assert property문과 다름
assert, assert property는 일부 수준의 기능적 커버리지를 제공
=>어써션 성공 시 일정시간 동안 변수 집합이 사용된 것이나 모든 선택적 경로가 테스트된 것은 아님(따라서 기능적 커버리지 필요)

Expectation
expect문은 프로퍼티 평가를 기다리게 해주는 절차적 블로킹 문장임
검증적 의미보다는 프로퍼티를 사용한 동기화 기능을 제공하므로 엄밀히 따르면 SVA는 아님
