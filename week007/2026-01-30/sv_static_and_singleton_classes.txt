OOP의 목표 중 하나는 전역 변수, 전역 메서드를 없애는 것(유지 보수 쉬워짐 + 이름 충돌 가능성 줄여줌)

때때로 전역변수가 정말로 필요한 경우가 있으며 예시로 모든 방법론들이 메세지를 필터링하고 에러를 셀 수 있게 해주는 프린트 서비스를 제공해주는 것임
이 프린트 클래스가 Dynamic class라면 테스트벤치의 구성요소의 모든 곳에서 인스턴시에이티드되어야 함=> 메모리 차지 많아짐

반면 싱글톤 클래스의 경우 
static class의 모든 변수, 메서드에 static 키워드가 붙어야 하고, 이 클래스에 대한 핸들이 없기에 테스트벤치에서 전달 불가능 하며, 사용하지 않더라도 할당된다는 단점을 보완해줌
싱클톤 클래스는 다음과 같은 특징을 가짐
-하나의 인스턴스만 있음
-non static임( 한 번만 생성됨)
-처음에 생성하기 더 어려우나 생성 후 프로그램을 더 간편화 해줌
  -싱글톤을 static 클래스 멤버가 아니라 단일 인스턴스 형태로 구현 시 필요할 때만 생성하는 지연 초기화(lazy initialization) 가능
싱글톤 패턴을 구현하기 위해 클래스의 인스턴스가 존재하지 않으면 새로 생성하는 메서드를 가진 클래스 생성, 이미 존재하면 그 객체를 가리키는 핸들 반환
객체가 다른 어떤 방식으로도 인스턴시에이티드 될 수 없게 생성자를 protected로 설정 해야함

검증에서 정적 클래스를 사용하는 또 다른 용도로 설정파라미터들을 저장하는 데이터베이스로 이용하는 것임
작은 시스템의 경우 설정파라미터들을 단일 클래스 또는 클래스의 계층에 간단히 저장 후 테스트벤치에서 전달 가능하나 규모가 커지면 핸들을 계층의 위아래로 전달할 때 매우 복잡
=> 대신 테스트벤치가 접근 가능하고, 이름으로 인덱스화된 파라미터의 전역 데이터베이스 이용
일반 데이터 베이스의 문제점 = 다른 타입의 값을 저장할 필요가 있으며 여러 타입들을 공통의 데이터베이스에 쉽게 저장할 수 있는 방법이 없음 => 파라미터화 사용

  실제 데이터베이스의 경우 인스턴스명을 가지고 있을 수 있으나 다음의 코드에서는 모든 이름을 하나로 이어붙여 인덱스 생성
  또한 지역변수로 설정시 그 범위 안에서만 사용가능하므로 전역지역으로 옮기고 static으로 사용
  UVM 데이터베이스는 와일드카드와 기타정규표현식을 허용해 associate 배열보다 더 복잡한 검색 방식 필요

  class config_db #(type T = int);
    static T db[string]; // type이 T인 데이터베이스, associative array로 구현함

static function void set(input string name, input T value);
db[name] = value;
endfunction

static function void get(input string name, ref T value);
value = db[name];
endfunction

static function void print();
$display("Configuration database %s", $typename(T));
foreach(db[i])
$display("db[%s]=%p",i,db[i]);
endfunction
endclass
