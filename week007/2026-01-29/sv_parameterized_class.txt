일반 클래스로 스택과 같은 지료 구조를 만들면 데이터 타입마다 전부다 작성을 해야 할 수 있다. 또한 클래스의 급증으로 빠르게 이어질 수 있다.
따라서 파라미터화된 클래스를 사용할 수 있으며 c++의 template과 유사하다

parameter int SIZE = 100;
class Stack #(type T = real); //파라미터화된 클래스에 구체적인 값들을 지정하는 단계를 특수화(specialization)이라 한다.
  local T stack[SIZE];
  local int top;

  function void push(input T i);
    stack[top++] = i;
  endfunction

  function T pop();
    return stack[--top];
  endfunction
endclass

이렇게 파라미터화된 클래스의 특수화의 경우 완전히 새로운 데이터 타입을 형성하는 것으로 볼 수 있다, 즉 상속, 다형성 등의 OOP관계가 깨져버린다.
OOP관계를 다시 생성하기 위해 공통된 클래스에서 확장되도록 만들 수 있다. 다음과 같이 아무것도 안 가지고 있을 수도 있다.
class GenBase;
endclass

parameterized class suggestion
  1.파라미터화된 클래스의 생성시 non-parameterized 클래스를 확실히 디버그 하고 parameter를 추가하라 (디버그에 드는 수고가 줄어들 것이다.)
  2. 트랜잭션 클래스 내 공통적인 가상 메서드 집합은 파라미터화된 클래스 생성 시 우리에게 도움을 줄 수 있다.
  -Generator 클래스는 copy 메서드가 항상 같은 시그니처를 가진다는 것을 알고 copy 메서드를 사용한다.
  $cast(tr, blueprint.copy()); 에서 blueprint가 Transaction인지 BadTr인지 신경 쓸 필요가 없어진(generator 타입에 독립적)
  다형성으로 인해 항상 올바른 루틴 호출이 가능해진다.
  -display 메서드는 트랜잭션이 데스트벤치 구성요소를 통해 흐를 때 쉽게 트랜잭션을 디버그할 수 있게 해준다.
  새 트랜잭션 추가가 쉬워진다. generator 는 수정할 필요가 없다.
  3.시스템 함수 $typename(), $bits()는 클래스가 파라미터의 너비, 이름을 알 필요가 있을 때 유용하다.
  -$typename의 경우 파라미터 타입의 이름을 반환한다. 
  -$bits의 경우 파라미터의 너비 반환, 구조체, 배열 등 복잡한 타입의 경우 표현을 비트스트림으로 저장하는 데 필요한 비트 수를 반환한다.
  4. 매크로를 파라미터화된 클래스의 대안으로 사용 가능하다
  -같은 트랜잭션 타입을 공유하는 여러 관련된 클래스 정의가 필요한 경우 파라미터화된 클래스나 하나의 거대 매크로 사용 가능
  => 즉 클래스 정의 방식보다 그 안에 어떤 데이터와 메서드를 담을지가 중요
