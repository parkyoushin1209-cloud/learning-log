검증 과정
1-하드웨어 명세 확인(기능 요구사항, 프로토콜 규칙, error case, illegal case 정의)
2-layered testbench 구성
3-constraint random testing(error, protocol violation등을 수정)
4-functional coverage(검증 완료? 아닐 경우 3번 반복)

layered testbench structure ---> 복잡해 보일 수 있으나 실제로는 코드를 각각 쪼개서 더 다루기 쉽게 만듬
                test
---------------------------(environment)-----------|
scenario   ||     generator                        |
---------------------------------------------------|
functional ||   agent     scoreboard      checker  | ---- functional coverage 
---------------------------------------------------|
command ||      driver    assertion       monitor  |
-------------------------------------------------- |
                            DUT
agent: tranaction를 받아 여러 명령어로 분해 주위로 전파
scoreboard: 명령어를 받고 결과 예측 및 monitor로 전달
checker: 예측 값과 monitor로부터 받은 실제 값을 비교
driver: 입력 구동
monitor: DUT출력 받음
generator: 랜덤 값 제공
environment는 기본 세팅이고 이후 여러 테스트에서 사용 가능

테스팅
block수준 test: 로직 정확성, corner case확인을 목적으로 사용/디버깅이 쉬움 functional coverage 확보 쉬움(제어가능성과 관측성이 높음)
sub-system수준: 인터페이스, 프로토콜 확인 목적/ IP간 연동 문제 발견 가능
system 수준: 통합동작, 실사용 시나리오 확인 목적 , 시뮬레이션이 느리고 버그 재현이 힘듬

directed testing(특정 시나리오를 의도적으로 작성)
단점: 작성 비용이 크다, 커버리지 한계 명확, 예상 못한 버그를 잡을 수 없다.
장점: 디버깅이 쉽고 테스트 의도 명확, 제현성 높고 빠름, bring-up에 유리(-> 설계가 기본적 기능을 하는가?)

constrained random testing
단점: 재현이 어렵다(seed 관리 필요), 의미 없는 패턴 많음, 특정 상태 도달이 어려움
장점: 예상 못한 버그 발견에 강함, corner case 자동 탐색, 커버리지 확장에 유리, regression에 적합(기존에 잘 되던게 여전히 잘되는지 확인)

실제로는 초기 검즘, 특정 기능 확인 단계에서 directed testing, 안정화 이후, 대규모 검증 단계에서 constrained random testing을 같이 사용함
